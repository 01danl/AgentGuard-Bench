# Minimal v0.2 proposal — not implemented

Status: proposal following the controlled runtime validation of v0.1. This document
does not change any implemented research definition, threshold, report or default.
The gate below was met for **one controlled real-model run** by
[RWV-003](real-model-validation.md) on 2026-10-28. That run is not a natural-task sample,
a recovery result or a causal comparison.

## Gate before implementation

Obtain a real-model Harness v4 export with at least one direct repeat-tool reminder.
Reconcile its call/result pairing, delivery handoff, baseline uncertainty and following
window manually. Keep the no-guard RWV-001 and scripted-model RWV-002 evidence distinct.
The current controlled examples cannot establish model recovery or causal guard benefit.

RWV-003 supplies one such export. The model made three identical reads, received the real
notice, and then produced no fourth tool call. The Analyzer's `UNKNOWN` reaction and all
counts agree with the raw-event reconciliation. The task was not completed, so the run is
evidence of delivery and observation, not of recovery or benefit.

## Smallest useful behavioral-analysis increment

1. Define an explicit, independently assessable progress/success criterion for each
   selected task. The criterion may be a reviewed workspace state or a task check;
   it must not be inferred from changing a tool call or `isError: false`.
2. Add a small manual annotation artifact referencing input hash, session, event seqs,
   criterion and evidence. Keep uncertain incidents unknown. Decide the label vocabulary
   through an explicit research review before changing the schema or computing metrics.
3. Compare existing repetition and reaction observations with those annotations on a
   small exploratory set, including legitimate polling, useful failing checks and mixed
   tool batches. Inspect disagreements before adding another detector or heuristic.

Acceptance: source observations remain traceable, existing v0.1 reports remain stable,
and any recovery label has independent evidence. A small pilot is diagnostic, not a
population-level efficacy claim. No automatic judge, dashboard or generic plugin system.

## Next proposed step after RWV-003 — not started

The smallest informative follow-up is a manual annotation of RWV-003 plus one no-guard
companion, not a runner. Reuse the same prompt, model, workspace inputs, tool scope and
time/output bounds, with fresh state and no warning insertion. Predeclare completion as the
four `probe.txt` reads followed by the `alternative.txt` read, annotate both raw logs with
their evidence, and retain `UNKNOWN` or `not_completed` where the evidence is insufficient.
This pair can test whether the observed stop is specific to the guard notice; it cannot
estimate efficacy. A multi-task pilot or the A/B runner should be considered only after
that diagnostic comparison.

## Preparation for a later A/B runner

Specify the experimental protocol before implementing orchestration:

- Pair task/environment/model/policy configurations; reset workspaces between trials.
- Vary only guard enablement within each pair, with recorded thresholds and exclusions.
- Randomize arm order and repeat trials; do not assume provider seeds guarantee determinism.
- Predeclare an independent task-success check and failure/timeout handling.
- Bound calls, time and spending; isolate credentials and retain log provenance privately.
- Separate task outcomes, process observations and provider-reported token accounting;
  keep unavailable fields null. Choose uncertainty estimates for the actual paired design
  once sample sizes and data are available, rather than inventing confidence from a demo.

The runnable A/B system remains the planned v0.3 scope. There is no runner implementation
or causal-effect estimate in this proposal.
